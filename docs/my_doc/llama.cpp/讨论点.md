## llama.cpp中跟设备相关数据结构
### 驱动注册
``` c++
struct ggml_backend_reg_i {
	// 返回该后端注册的短名称字符串（如 "CPU"、"CUDA"）
	// 参数1 reg：指向具体的 ggml_backend_reg 实例
	const char * (*get_name)(ggml_backend_reg_t reg);

	// 该后端当前能枚举到的设备个数
	// CPU 后端常常是 1（一个逻辑 CPU 设备）；GPU 后端通常是 GPU 数量；
	size_t             (*get_device_count)(ggml_backend_reg_t reg);
	
	// 按 index 取出第 index 个设备的 ggml_backend_dev_t 句柄
	// 设备句柄绑定了另一张表 ggml_backend_device_i：在上面才有 init_backend（创建真正干活的 ggml_backend_t 流）、get_buffer_type、supports_op 等。
	ggml_backend_dev_t (*get_device)(ggml_backend_reg_t reg, size_t index);
	

	// (optional) get a pointer to a function in the backend
	// backends can add custom functions that are not part of the standard ggml-backend interface
	// 用字符串名字取该后端提供的额外 C 函数指针，返回 void *，调用方再强转成具体函数类型。
	void * (*get_proc_address)(ggml_backend_reg_t reg, const char * name);
};
```

ggml_backend_reg_i 描述的是某一种后端实现在“注册表”这一层的虚表：上层通过 ggml_backend_reg_t 找到该后端，再用这几个函数拿到人类可读的名字、设备列表以及扩展入口。
	
```c++
struct ggml_backend_reg {
	int api_version; // initialize to GGML_BACKEND_API_VERSION
	struct ggml_backend_reg_i iface;
	void * context;
};
```
角色： 表示某一种后端实现在进程里的注册入口，例如 CPU、CUDA、Vulkan 各对应一个 reg（或由动态库 ggml_backend_init 返回）。
作用： 按名字识别插件；枚举本插件下有多少台逻辑设备；用索引拿到 ggml_backend_device；按字符串取扩展函数指针。

### 设备
ggml_backend_device_i（单设备能力：建 backend stream、buffer 类型、supports_op 等）是两层：reg = 一类插件 / 驱动；dev = 该插件下的某张卡或某个逻辑设备。
ggml_backend_device_i 是单个设备（ggml_backend_dev_t）的虚表：描述“这台设备叫什么、有多少显存、能算什么、用什么 buffer、怎么建真正干活的 backend”。上层通过 ggml_backend_dev_* 包装函数调用这些指针。

```c++
struct ggml_backend_device_i {
	// device name: short identifier for this device, such as "CPU" or "CUDA0"
	const char * (*get_name)(ggml_backend_dev_t dev);

	// device description: short informative description of the device, could be the model name
	// 更可读的说明，例如 GPU 型号、厂商字符串，给人看或做诊断
	const char * (*get_description)(ggml_backend_dev_t dev);

	// device memory in bytes: 0 bytes to indicate no memory to report
	// free: 可用; total: 总设备内存；0 表示无可报告内存
	void         (*get_memory)(ggml_backend_dev_t dev, size_t * free, size_t * total);

	// device type, GGML_BACKEND_DEVICE_TYPE_*, 有CPU、GPU、IGPU、ACCEL、META等可选
	enum ggml_backend_dev_type (*get_type)(ggml_backend_dev_t dev);

	// device properties
	// 填充 props 各字段：name、description、memory_free、memory_total、type、device_id、caps（async、host_buffer、buffer_from_host_ptr、events）
	void (*get_props)(ggml_backend_dev_t dev, struct ggml_backend_dev_props * props);

	// backend (stream) initialization
	// 把“设备”变成能 ggml_backend_graph_compute、传 tensor、同步的对象。
	// 在已经抽象好的 设备句柄 ggml_backend_dev_t 设备上，创建一个可实际干活的运行时对象 ggml_backend_t
	ggml_backend_t (*init_backend)(ggml_backend_dev_t dev, const char * params);

	// preferred buffer type
	// 决定权重/激活在哪类内存上分配（设备显存 vs 系统内存等），以及 API: ggml_backend_buft_alloc_buffer 的行为。
	ggml_backend_buffer_type_t (*get_buffer_type)(ggml_backend_dev_t dev);

	// (optional) host buffer type (in system memory, typically this is a pinned memory buffer for faster transfers between host and device)
	// 在 CPU 上分配 staging，加速与该设备之间的拷贝。
	// 场景：异步 H2D/D2H、ggml_backend_tensor_copy_async 路径；caps.host_buffer 为 true 时通常可用。
	// 以 CUDA 为例，ggml-cuda.cu 里用的是 cudaMallocHost（pinned / page-locked host memory），释放用 cudaFreeHost。指针给 CPU 用，GPU 通过 DMA 读写这块内存，数据并不住在 GPU 显存里。
	ggml_backend_buffer_type_t (*get_host_buffer_type)(ggml_backend_dev_t dev);

	// (optional) buffer from pointer: create a buffer from a host pointer (useful for memory mapped models and importing data from other libraries)
	// mmap 模型文件、外部库导出的内存，减少一份 memcpy。
	// 大模型 mmap 权重；与 GGML_BACKEND_BUFFER_USAGE_WEIGHTS 等配合。
	ggml_backend_buffer_t (*buffer_from_host_ptr)(ggml_backend_dev_t dev, void * ptr, size_t size, size_t max_tensor_size);

	// check if the backend can compute an operation
	// 图划分、fallback 的核心能力探测
	// 场景： 调度器为每个 node 选 backend；某 dtype/某 op 仅 CPU 支持时自动落 CPU。
	bool (*supports_op)(ggml_backend_dev_t dev, const struct ggml_tensor * op);

	// check if the backend can use tensors allocated in a buffer type
	// 多设备混用时避免“算子在 GPU 上跑，数据却在 GPU 无法访问的 buffer 里”。
	// 场景： CPU/GPU 分裂权重；判断是否需要 ggml_backend_tensor_copy / tensor_copy_async。
	bool (*supports_buft)(ggml_backend_dev_t dev, ggml_backend_buffer_type_t buft);

	// (optional) check if the backend wants to run an operation, even if the weights are allocated in an incompatible buffer
	// these should be expensive operations that may benefit from running on this backend instead of the CPU backend
	bool (*offload_op)(ggml_backend_dev_t dev, const struct ggml_tensor * op);

	// (optional) event synchronization
	// 设备侧细粒度同步（类似 CUDA event）：event_record / event_wait 在 ggml_backend_i 上与具体 stream 配合；设备级提供创建/释放/同步语义。
	ggml_backend_event_t (*event_new)         (ggml_backend_dev_t dev);
	void                 (*event_free)        (ggml_backend_dev_t dev, ggml_backend_event_t event);
	void                 (*event_synchronize) (ggml_backend_dev_t dev, ggml_backend_event_t event);
};

```

### 设备存储

struct ggml_backend_buffer_type_i {
	const char *          (*get_name)      (ggml_backend_buffer_type_t buft);
	// allocate a buffer of this type
	ggml_backend_buffer_t (*alloc_buffer)  (ggml_backend_buffer_type_t buft, size_t size);
	// tensor alignment
	size_t                (*get_alignment) (ggml_backend_buffer_type_t buft);
	// (optional) max buffer size that can be allocated (defaults to SIZE_MAX)
	size_t                (*get_max_size)  (ggml_backend_buffer_type_t buft);	// 对这种 buffer type，单次 alloc_buffer 建议/允许的最大字节数是多少
	// (optional) data size needed to allocate the tensor, including padding (defaults to ggml_nbytes)
	// 在某个 buffer_type（某种设备/内存策略）上，为给定 ggml_tensor 实际要占用的字节数
	// 		逻辑上的张量大小（元素个数 × 类型）和 该后端内核实际读写的内存布局 可以不一致(后端可能要对行宽做补齐，避免越界或未对齐访问)
	size_t                (*get_alloc_size)(ggml_backend_buffer_type_t buft, const struct ggml_tensor * tensor);
	// (optional) check if tensor data is in host memory and uses standard ggml tensor layout (defaults to false)
	bool                  (*is_host)       (ggml_backend_buffer_type_t buft);
};

struct ggml_backend_buffer_type {
	struct ggml_backend_buffer_type_i  iface;
	ggml_backend_dev_t device;
	void * context;
};
角色： 描述某一类内存如何分配与解释，而不是某一块已经申请好的内存。例如：“CUDA 设备内存”、“Metal 上的 buffer”、“CPU 普通页”等，各自是一个 buffer_type 对象。
作用： gml_backend_buft_alloc_buffer(buft, size) → 得到 ggml_backend_buffer；查询对齐、是否 host、最大分配等。
和 ggml_backend_device 的关系： 多对一：同一 device 可有多种 buffer_type（默认设备内存 + 可选 host/pinned 等）；每个 buffer_type 绑定一台 device（ggml_backend_buft_get_device）。

struct ggml_backend_buffer_i {
	// (optional) free the buffer
	void         (*free_buffer)  (ggml_backend_buffer_t buffer);
	// base address of the buffer
	void *       (*get_base)     (ggml_backend_buffer_t buffer);
	// (optional) initialize a tensor in the buffer (eg. add tensor extras)
	// 张量已经放进某块 ggml_backend_buffer 之后，由后端再做一层 “收尾初始化”（例如挂 tensor->extra、对 padding 做清零等）。通用入口是 ggml_backend_buffer_init_tensor：若 buffer->iface.init_tensor 非空则调用。
	enum ggml_status (*init_tensor)(ggml_backend_buffer_t buffer, struct ggml_tensor * tensor);
	// tensor data access
	void         (*memset_tensor)(ggml_backend_buffer_t buffer,       struct ggml_tensor * tensor,     uint8_t value, size_t offset, size_t size);
	void         (*set_tensor)   (ggml_backend_buffer_t buffer,       struct ggml_tensor * tensor, const void * data, size_t offset, size_t size);
	void         (*get_tensor)   (ggml_backend_buffer_t buffer, const struct ggml_tensor * tensor,       void * data, size_t offset, size_t size);
	// (optional) 2d data copies
	void         (*set_tensor_2d)(ggml_backend_buffer_t buffer,       struct ggml_tensor * tensor, const void * data, size_t offset, size_t size, size_t n_copies, size_t stride_tensor, size_t stride_data);
	void         (*get_tensor_2d)(ggml_backend_buffer_t buffer, const struct ggml_tensor * tensor,       void * data, size_t offset, size_t size, size_t n_copies, size_t stride_tensor, size_t stride_data);

	// (optional) tensor copy: dst is in the buffer, src may be in any buffer, including buffers from a different backend (return false if not supported)
	bool         (*cpy_tensor)   (ggml_backend_buffer_t buffer, const struct ggml_tensor * src, struct ggml_tensor * dst);
	// clear the entire buffer
	void         (*clear)        (ggml_backend_buffer_t buffer, uint8_t value);
	// (optional) reset any internal state due to tensor initialization, such as tensor extras
	void         (*reset)        (ggml_backend_buffer_t buffer);
};

struct ggml_backend_buffer {
	struct ggml_backend_buffer_i  iface;
	ggml_backend_buffer_type_t    buft;		// 通过这个实例 alloc buffer，然后再通过 iface 实例操作 这块 buffer
	void * context;
	size_t size;
	enum ggml_backend_buffer_usage usage;
};

角色：在某种 buffer_type 上真正分配出来的一块连续存储（或逻辑连续），张量的 data 会落在这块里（通过 init_tensor 等与 ggml_tensor 绑定）。
作用： ggml_backend_buffer_get_base 得地址；读写 tensor；ggml_backend_tensor_copy 在 buffer 之间拷贝；free 释放整池。
和 ggml_backend_buffer_type 的关系： 多对一：很多 buffer 可来自同一 buft；每个 buffer 引用一个 buffer_type；通过 buft -> device 间接属于某台设备。


	extra buft 包括（视编译与平台而定）：权重 repack 专用 buffer、AMX 等 CPU 加速路径的 buffer 等，都挂在 CPU 设备上，但和普通 ggml_backend_cpu_buffer_type() 不是同一种分配策略。

## 设备管理后端
struct ggml_backend_i {
	const char * (*get_name)(ggml_backend_t backend);

	void (*free)(ggml_backend_t backend);

	// (optional) asynchronous tensor data access
	// 把 data 指向的主机内存里一段数据，异步写入 tensor 在设备上的缓冲区（从 offset 起连续 size 字节）。
	// 语义上对应 set_tensor 的异步版：调用应尽快返回，不保证在返回时拷贝已完成；完成顺序由该 backend 的 stream 与 ggml_backend_event_* 等机制协调。
	void (*set_tensor_async)   (ggml_backend_t backend,       struct ggml_tensor * tensor, const void * data, size_t offset, size_t size);
	void (*get_tensor_async)   (ggml_backend_t backend, const struct ggml_tensor * tensor,       void * data, size_t offset, size_t size);
	void (*set_tensor_2d_async)(ggml_backend_t backend,       struct ggml_tensor * tensor, const void * data, size_t offset, size_t size, size_t n_copies, size_t stride_tensor, size_t stride_data);
	void (*get_tensor_2d_async)(ggml_backend_t backend, const struct ggml_tensor * tensor,       void * data, size_t offset, size_t size, size_t n_copies, size_t stride_tensor, size_t stride_data);
	bool (*cpy_tensor_async)(ggml_backend_t backend_src, ggml_backend_t backend_dst, const struct ggml_tensor * src, struct ggml_tensor * dst);

	// (optional) complete all pending operations (required if the backend supports async operations)
	void (*synchronize)(ggml_backend_t backend);

	// (optional) graph plans (not used currently)
	// compute graph with a plan
	ggml_backend_graph_plan_t (*graph_plan_create) (ggml_backend_t backend, const struct ggml_cgraph * cgraph);
	void                      (*graph_plan_free)   (ggml_backend_t backend, ggml_backend_graph_plan_t plan);
	// update the plan with a new graph - this should be faster than creating a new plan when the graph has the same topology
	void                      (*graph_plan_update) (ggml_backend_t backend, ggml_backend_graph_plan_t plan, const struct ggml_cgraph * cgraph);
	// compute the graph with the plan
	enum ggml_status          (*graph_plan_compute)(ggml_backend_t backend, ggml_backend_graph_plan_t plan);

	// compute graph (always async if supported by the backend)
	enum ggml_status          (*graph_compute)     (ggml_backend_t backend, struct ggml_cgraph * cgraph);

	// (optional) event synchronization
	// record an event on this stream
	void (*event_record)(ggml_backend_t backend, ggml_backend_event_t event);
	// wait for an event on on a different stream
	void (*event_wait)  (ggml_backend_t backend, ggml_backend_event_t event);

	// (optional) sort/optimize the nodes in the graph
	void                      (*graph_optimize)    (ggml_backend_t backend, struct ggml_cgraph * cgraph);
};


struct ggml_backend {
	ggml_guid_t guid;
	struct ggml_backend_i iface;
	ggml_backend_dev_t device;
	void * context;
};

角色：在某台 device 上创建的计算上下文/流：提交 ggml_cgraph（ggml_backend_graph_compute）、异步 tensor_set/get、synchronize、可选 event_record/event_wait 等。
作用： 在对应设备上执行算子；与别的 backend 之间 tensor_copy_async；查询默认 buft 等。
和 ggml_backend_device 的关系：由 device 创建： ggml_backend_dev_init(device, params) → ggml_backend_t；一个 device 上通常可以建多个 backend（多流），也可以只建一个；backend->device 指回该设备。

## plan

typedef void * ggml_backend_graph_plan_t;

设计意图：针对某个 ggml_cgraph，在 ggml_backend_t 上做一次**“编译/规划”，把图结构、算子顺序、资源需求等固化到可复用的计划对象**里；之后多次执行同一拓扑时走 ggml_backend_graph_plan_compute(backend, plan)，避免每次从零解析整图。

相关 API（与 ggml_backend_i 的对应关系）：
	ggml_backend_graph_plan_create(backend, cgraph) → 调用 backend->iface.graph_plan_create，得到 plan。
	ggml_backend_graph_plan_free(backend, plan) → graph_plan_free。
	ggml_backend_graph_plan_compute(backend, plan) → graph_plan_compute。
	内部虚表里还有 graph_plan_update(backend, plan, cgraph)：在拓扑不变（或兼容）时用新 cgraph 更新已有 plan，比销毁再创建更省（公开 C API 里未必全部包装出来，以头文件为准）。

## ggml_tensor 数据类型
```c++
   // n-dimensional tensor
    struct ggml_tensor {
        enum ggml_type type;

        struct ggml_backend_buffer * buffer;

        int64_t ne[GGML_MAX_DIMS]; // number of elements
        size_t  nb[GGML_MAX_DIMS]; // stride in bytes:
                                   // nb[0] = ggml_type_size(type) -> 是“最小存储单元”大小，不一定等于一个逻辑元素大小（量化时尤其明显）。
                                   //         nb[0] 不是“逻辑元素字节数”，而是“底层存储单元字节数”。对 F32 它恰好就是 4,对 Q4_0 它是一个 block 的大小（18）
                                   // nb[1] = nb[0]   * (ne[0] / ggml_blck_size(type)) + padding -> 是跨 ne[0] 这一整行（或一段 block）的步长。
                                   // nb[i] = nb[i-1] * ne[i-1]  -> 更高维继续乘下去，得到标准多维 stride
                                        // ggml_type_size(type)：一个存储块占多少字节（type_size）
                                        // ggml_blck_size(type)：一个存储块对应多少个逻辑元素（blck_size）

                                        // 普通类型（F32/I32）: blck_size = 1，所以 1 个存储块就是 1 个逻辑元素。
                                        // 量化类型（如 Q4_0）: blck_size > 1, QK4_0 = 32，一个 block_q4_0 存 32 个逻辑值（外加 scale 等元数据）。

        // compute data
        enum ggml_op op;

        // op params - allocated as int32_t for alignment
        int32_t op_params[GGML_MAX_OP_PARAMS / sizeof(int32_t)];

        int32_t flags;

        struct ggml_tensor * src[GGML_MAX_SRC];

        // source tensor and offset for views
        struct ggml_tensor * view_src;
        size_t               view_offs;

        void * data;

        char name[GGML_MAX_NAME];

        void * extra; // extra things e.g. for ggml-cuda.cu

        char padding[8];
    };
```
其中： 
- `buffer` 是存储当前tensor数据域的大空间
- `data` 是当前 tensor 数据域在 buffer 中的地址（buffer 首地址 + offset）
- `ne[]` 是当前 tensor 数据的 shape
- `nb[]` 是当前 tensor 数据的 stride

## shape-node
shape-node 常用有： reshape、view、permute、transpose
连续 node： **contiguous**

llama.cpp 和 NPU 状态之间的 gap：
- llama.cpp 中的实现
    - llama.cpp 在构建计算图的过程中，会根据计算逻辑，加入 shape-node
    - 这些 shape-node 在构建计算图时，已经对 tensor 的 `ne[]` 和 `nb[]` 进行了处理
    - 这些 shape-node 在前向计算过程中，什么都没有做！！！
    - shape-node 后的 compute-node 会根据 shape-node 的 `ne[]` 、`nb[]` 信息，在 data 域中获取正确的数据

- NPU 上的状态
    - reshape、transpose、permute等shape-node 操作，真的是在搬移数据
    - 后续的 compute-node 会获得连续的数据排布

- gap：
    - 如果在llama.cpp的实现中，前向过程调用NPU的 shape-node 搬移数据成连续状态，那么 shape-node 的 `ne[]` 和 `nb[]` 将会出现差错，后续调用 NPU 的compute-node 计算过程虽然不会出错，但在 shape-node 复用的条件下，取数据的逻辑全乱了。
        - llama.cpp 的关于 tensor 的设计初衷被改变，因此 llama.cpp 针对不同的模型的通用性不再存在，需要因此定制化适配不同的模型

- 解决办法：

如果在llama.cpp的实现中，前向过程中 shape-node 不做任何动作，那么在后续的 compute-node 计算中，可考虑这两种修改方案：
- 计算前取数据的时候，根据输入 node 的 shape 和 stride 进行正确的获取，
    - 优点：避免了数据的拷贝开销
    - 缺点：对要求数据连续性的所有的 compute-node 都要修改，甚至修改计算的逻辑，工作量略大

- 实现 **contiguous** 算子，在 compute-node 计算逻辑中，先调用 contiguous 算子，将 tensor 的 data 复制成连续的
    - 优点：compute-node 的实现是自定义了，计算前先调用 **contiguous** 算子即可，compute-node 算子修改小
        - 因为 **contiguous** 算子是一个拷贝操作，因此不会改变 shape-op 的 shape 和 stride
        - 据调研结果，compute-node 计算结果的连续性，由 compute-node 自己的 view_src 或者 生成compute-node时的 `ne[]` 、 `nb[]`信息确定，和输入的shape和stride无关。不会影响整体逻辑。
    - 缺点：需要对操作数进行一次拷贝，增加了开销


# 3 计算图的调度

**优先级： 中**

目的：
    如何让计算图整体运行在NPU上，运行过程中不与CPU交互

一个计算图的执行状态：
- **权重在 NPU 上**
- **计算过程中的中间状态在NPU上**
- 计算图在 host上
- 调度逻辑在 host 上
- host 空置计算流程，适时下发带执行的OP -- eagle 模式
- 只有部分 OP 的执行过程在 NPU上

原因：
- 不同的输入 shape 对应了不同的计算图
    - 多请求的 个数 不同，shape也不同
    - n_batch 如果不一定能被 n_ubatch 整除，shape 中 n_tokens 维度上，在 [1, n_ubatch) 内动态随机
    - 因此计算图的数量是不确定的，但肯定不是一两个


tradeoff：
- 算子融合 + 自定义 OP
    - 通用的处理方式
    - 需要修改计算图构造逻辑
    - 需要修改前向计算逻辑

- prefill/decode分离
    - prefill 放在 host 上实现
    - decode 放在 NPU 上实现
        - 只支持 batch 为 1/2/3/4 等几种shape的计算图
        - decode 开始前，在 host 上根据 shape 信息，选择需要参与计算的计算图

- 固定 n_ubatch
    - prefill阶段构建两种类型的计算图，一种计算图放在 NPU 上执行，一种在 host 端执行
        - 构建 n_tokens / n_ubatch （取整）个 n_ubatch 大小的计算图。prefill 阶段这部分，选择这个图，在 NPU 上执行计算
        - 对于 n_tokens % n_ubatch 这种不确定大小的计算图，放在 host 上执行
    - decode 放在 NPU 上实现
        - 只支持 batch 为 1/2/3/4 等几种shape的计算图
        - decode 开始前，在 host 上根据 shape 信息，选择需要参与计算的计算图
